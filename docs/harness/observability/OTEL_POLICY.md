# OpenTelemetry Policy

Instrumentar UI/API, autorização, consultas ao banco, AgentRun, delegação Eve, tool/API, AI Gateway, geração criativa, approvals e conectores. Propagar `traceparent` entre serviços sob controle; validar/sanitizar contexto de entrada não confiável e limitar propagação para terceiros. OpenTelemetry oferece correlação distribuída por contexto; [referência oficial](https://opentelemetry.io/docs/concepts/context-propagation/). Vercel Observability pode ser destino, mas o contrato não depende do dashboard específico.

Service names estáveis: `marketing-os-web`, `marketing-os-api`, `marketing-agents`, `marketing-integrations`. `trace_id`, `agent_run_id`, `agency_id`, `client_workspace_id`, `product_id`, `campaign_id`, `artifact_id`, `approval_id` servem para investigação em traces protegidos; IDs de alta cardinalidade não viram labels de métricas agregadas. Contagens/latências por service, agent, channel, status e environment são métricas controladas. AI telemetry registra modelo/provider, versão de prompt, tokens, custo, latência, tool calls e fallback; conteúdo integral de prompt fica fora por padrão.

Redigir passwords, access/refresh tokens, service role, headers de autorização, PII e conteúdo privado desnecessário antes de exportar. Sampling, retenção, acesso a traces e collector/drain são decisões de SPEC/ambiente. Smoke test de lançamento: uma Request percorre API → Eve → tool → artifact → approval com trace correlacionado, custos reconciliados e nenhum segredo; testar falha de integração e alerta. Alertas iniciais: cross-tenant deny anômalo, falha de AgentRun/conector, custo, timeout, fila e publicação incerta.
