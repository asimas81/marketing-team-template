# Supabase Auth e RLS Policy

Supabase Auth identifica usuário; autorização de negócio vem de membership e policy no banco/API. Cada tabela exposta exige grants mínimos e RLS por operação. Entidade de Agency filtra `agency_id`; entidade de Client filtra `(agency_id, client_workspace_id)` e membership/grant efetivo. Product/Campaign/Artifact/Approval/Integration verificam ownership transitivo por chave composta, impedindo vincular dois Clients. Views e funções são auditadas para não bypassar política; service role não é caminho normal de acesso.

Não usar `raw_user_meta_data` como fonte de papel porque é editável pelo usuário; claims JWT de membership podem ficar defasadas após remoção. Preferir consulta autoritativa a memberships/policy para ações sensíveis e testar revogação. `auth.uid()` sem autenticação é nulo; policy deve negar explicitamente sessão ausente. API repete validação para operações privilegiadas e service accounts. A [documentação oficial de RLS](https://supabase.com/docs/guides/database/postgres/row-level-security) e [segurança da Data API](https://supabase.com/docs/guides/api/securing-your-api) confirmam essas propriedades; SQL concreto fica para SPEC/migration futura.

Matriz de testes: cross-agency deny, cross-client deny na mesma Agency, owner/admin permitidos dentro de grants, manager sem atribuição negado, Client Viewer read-only, Client Approver apenas próprio Client, ID adulterado em URL/payload, FK cruzada, sessão removida, acesso direto à Data API e operação por service role delegada. Critério de saída exige testes positivos e negativos contra banco de teste isolado; existência da policy não basta. Nenhuma RLS foi criada nesta execução.

Na primeira fase de Email, `ChannelIdentity`, `ConsentRecord`, `SuppressionEntry`, `EngagementEvent` e `EngagementAction` exigem a dupla fronteira Agency/Client mesmo sem Lead completo. `Lead`, `LeadIdentity`, `ConversationThread` e `CrmHandoff` são futuros e seguem a mesma regra. Acesso a dados de contato e threads é mais restrito que acesso a Campaign: papel/finalidade/ação precisam ser verificados pela API e, para tabelas expostas, por grants/RLS correspondentes. Um mesmo email/telefone em outro Client não autoriza correlação, leitura ou reutilização de consentimento. Webhooks/service accounts devem resolver Client pela ClientIntegration validada antes da escrita; service role bypass não substitui essa checagem.
